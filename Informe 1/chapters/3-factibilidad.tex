\section{Estudio de factibilidad}

\subsection{Análisis técnico}

El desarrollo de Coord-Agent requiere evaluar la viabilidad de sus funcionalidades principales: interpretación de lenguaje natural, extracción de disponibilidad y cálculo de horarios. Para ello se analizan las herramientas de desarrollo, los modelos de lenguaje, las APIs externas y los recursos computacionales necesarios.

En cuanto al stack tecnológico, el frontend se implementa en React 18 con TypeScript y Vite, lo que permite construir una SPA con actualización en tiempo real. El backend utiliza FastAPI con Uvicorn como servidor ASGI, siguiendo el patrón BFF (Backend for Frontend), que establece que el frontend nunca debe comunicarse directamente con el proveedor LLM. La validación de datos se realiza con Pydantic v2, asegurando consistencia estructural entre todos los módulos. Para el control de versiones se emplea GitHub.

Respecto al modelo de lenguaje, el sistema soporta múltiples proveedores configurables mediante variables de entorno, lo que otorga flexibilidad para desarrollo, pruebas y demostración. Como proveedor principal se utiliza Gemini 3.0 Flash de Google, accedido mediante API REST con autenticación por clave almacenada en el archivo \texttt{.env} del backend y temperatura 0,1, dado que la tarea requiere extracción precisa, no creatividad. La salida se fuerza en formato JSON mediante \texttt{responseMimeType}. Como alternativa local se utiliza Qwen3-4B-Instruct en formato GGUF (Q4\_K\_M) ejecutado mediante \texttt{llama.cpp}. Además, el sistema cuenta con integración opcional mediante Ollama y un modo mock basado en reglas para desarrollo rápido. Ante fallos del proveedor configurado, el backend conmuta automáticamente a un extractor por reglas, garantizando continuidad operativa.

La arquitectura del MVP separa estrictamente cinco módulos: el frontend en React, el BFF en FastAPI que expone endpoints REST para sesiones, mensajes, cálculo y confirmación, el LLM Service encargado exclusivamente de convertir lenguaje natural en JSON estructurado, sin tomar decisiones, el Decision Engine motor Python determinista que cruza horarios y calcula las tres mejores opciones y el JSON Repository para persistencia simple en archivo. Esta separación garantiza que el LLM nunca decide y que, ante cualquier fallo del modelo, el usuario puede corregir datos manualmente y el motor opera igual.

En cuanto a recursos computacionales, al delegar la inferencia a la API de Gemini, los requisitos son mínimos: una laptop con 8 a 16 GB de RAM sin GPU basta para el desarrollo. Para producción se proyecta una VM cloud básica AWS t3.small o GCP e2 medium. En caso de optar por el modelo local Qwen 3-4B GGUF, este requiere aproximadamente 3 a 4 GB de RAM y presenta tiempos de inferencia de 10 a 30 segundos por solicitud en CPU.

Finalmente, en seguridad y privacidad se aplica minimización de datos solo se persiste información estructurada, no conversaciones completas, la clave de API nunca se expone al frontend, se implementa cifrado HTTPS en producción y se validan todas las salidas del LLM contra esquemas Pydantic. El prompt del sistema restringe el dominio a coordinación de actividades, filtrando solicitudes fuera de contexto. El análisis concluye que Coord-Agent es técnicamente factible dentro del semestre, con un stack accesible y una arquitectura modular que permite escalar sin rediseñar el núcleo.




\subsection{Análisis económico}

\subsubsection{Supuestos y alcance}

Para efectos de la evaluación económica se considera el desarrollo de un prototipo funcional orientado a pequeñas y medianas empresas que requieren coordinar reuniones y disponibilidades de equipos de trabajo mediante procesamiento de lenguaje natural.

El proyecto contempla una arquitectura cliente-servidor con backend en FastAPI, frontend web responsivo y utilización de modelos de lenguaje (LLM) externos para la extracción semántica de disponibilidad horaria desde mensajes escritos en lenguaje natural.

Dado que el desarrollo será realizado en contexto académico, se considera una valorización referencial de horas de trabajo equivalente a una beca de trabajo en la Universidad de Santiago de Chile. Esta valorización permite estimar el costo real de ingeniería requerido para construir el sistema.

\subsubsection{Costos operacionales}

Los costos operacionales del sistema corresponden principalmente a:

\begin{itemize}
    \item Infraestructura cloud para ejecución del backend.
    \item Consumo de API de modelos de lenguaje.
    \item Almacenamiento persistente y respaldos.
    \item Dominio y servicios auxiliares.
    \item Mantención y soporte técnico básico.
\end{itemize}

Debido a que el sistema no requiere procesamiento intensivo fuera de las consultas al modelo LLM, el principal costo variable corresponde al consumo de tokens utilizados en cada interacción procesada.

\begin{itemize}

\subsubsection{Estrategia de monetización}

El modelo de negocio propuesto considera la comercialización del sistema bajo modalidad SaaS (Software as a Service), cobrando una suscripción mensual a empresas interesadas en automatizar la coordinación de reuniones y disponibilidad de equipos.

Debido al bajo costo operacional por cliente, el sistema presenta márgenes operacionales elevados incluso utilizando tarifas relativamente accesibles para pequeñas y medianas empresas.

Se propone un valor de suscripción entre \$25.000 y \$50.000 CLP mensuales por empresa, dependiendo de:

\begin{itemize}
    \item Cantidad de usuarios registrados.
    \item Integraciones disponibles.
    \item Límite de consultas mensuales.
    \item Funcionalidades premium.
    \item Nivel de soporte ofrecido.
\end{itemize}

\subsubsection{Escalabilidad económica del sistema}

Uno de los principales atributos económicos del sistema es su bajo costo marginal por cliente adicional. La mayor parte de los costos operacionales corresponden a infraestructura base y mantención, mientras que el consumo asociado al procesamiento mediante modelos LLM representa un costo relativamente reducido incluso bajo escenarios de uso intensivo.

Debido a que la arquitectura propuesta utiliza servicios cloud escalables y procesamiento externo mediante APIs, el sistema puede aumentar progresivamente su capacidad sin requerir rediseños importantes de infraestructura.

En escenarios de crecimiento, el incremento de costos operacionales se concentra principalmente en:

\begin{itemize}
    \item Mayor capacidad de cómputo del servidor backend.
    \item Incremento del consumo mensual de tokens LLM.
    \item Mayor almacenamiento persistente.
    \item Aumento de requerimientos de soporte y monitoreo.
\end{itemize}

Sin embargo, el crecimiento de estos costos no es lineal respecto al número de clientes, permitiendo mantener márgenes operacionales elevados incluso con una base moderada de empresas activas.

Por ejemplo, duplicar la cantidad de empresas no implica necesariamente duplicar el costo de infraestructura, ya que una misma instancia cloud puede soportar múltiples organizaciones simultáneamente durante las primeras etapas del proyecto.

Esto permite proyectar un modelo SaaS escalable y económicamente sustentable en el tiempo.

\subsubsection{Conclusiones económicas}

El análisis económico realizado evidencia que el sistema posee una estructura de costos favorable para un modelo SaaS basado en inteligencia artificial.

Los costos asociados al consumo de modelos LLM resultan significativamente bajos en comparación al valor agregado entregado por la automatización de coordinación grupal y extracción semántica de disponibilidad.

Adicionalmente, el sistema presenta características de alta escalabilidad, ya que el costo marginal por cliente adicional es reducido. Esto permite proyectar escenarios de rentabilidad positivos incluso con una base moderada de clientes.

En consecuencia, desde un punto de vista económico, el proyecto resulta técnicamente viable y potencialmente sustentable en un contexto de comercialización real.
